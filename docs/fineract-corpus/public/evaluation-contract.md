# Public evaluation contract snapshot — Issue #37

- 各課題について、変更要求、維持する仕様、意図して変える既存挙動、評価対象外を公開し、requirement IDから根拠と観測へ追跡する。
- baselineの未変更成果物、妥当な参照実装、要求を破る複数の変異、評価環境障害を同じ通常採点入口で区別する。参照実装と非公開テストはworkerから隔離する。資料選択を先に封印し、gold patchはその後に作る。
- Java/Gradleを使った実コードのbuild・JUnitと、対象公開API/DB/COBを通る代表シナリオで採点する。別実装の小さなPython関数や文字列検査でFineractの実行を代用しない。
- 採点は提出物の固定copyを使い、新しいDB/一時領域で実行する。test実行数0/skip/build障害/環境障害を合格へ変換しない。
- 既存テストで新要求と衝突する箇所は前もって例外台帳に固定する。結果を見て期待値を変更しない。その他の関連回帰を維持する。
- 正常/境界/不正入力・保存・状態変化を個別に残す。既知の製品失敗は保持し、未実行の項目はblocked、評価器障害はunknown。qualityのnullを0やpassにしない。
- 変異は(a)resume inclusiveのまま、(b)全周年型を無条件月末にする、(c)filterを常に無視する/権限を落とす等、要求の本質を破るものを選ぶ。許容される実装形を不当に拒まない。
